# Lovetry 全面质量审查与整改基线

> 审查日期：2026-08-07
> 审查基线：`main@27be047c5f4062716866e6448d4ad12fcae483ed`
> 整改分支：`agent/lovetry-audit-hardening`
> 方法：沿用 SafeHome 的事实基线 → 分层审查 → 风险分级 → 小步整改 → 自动验证 → 真实环境验收方法。
> 边界：本轮可以核查 GitHub 代码、配置、测试、文档和提交事实；真实 AppID、CloudBase 控制台规则、双/三账号、微信开发者工具、iOS/Android 真机、屏幕阅读器和真实模型输出仍需要外部环境验收。

## 1. 结论

Lovetry 已经不是演示原型，而是一个具备明确产品结构、权限意识、自动测试、CloudBase 后端、数据备份、媒体、关系互动和 AI Agent 的中等复杂度微信小程序。

当前主要问题已经从“缺功能”转变为“发布可信度不足”：

1. 历史数据兼容存在敏感记录可见性风险；
2. 解绑后的历史数据权利模型不完整；
3. Agent 安全评测覆盖面不足，真实模型尚未人工红队；
4. 本地临时数据和同步游标缺少明确的用户/情侣空间作用域；
5. 数据 Schema、幂等、备份恢复和 CloudBase 真实环境仍有工程缺口；
6. 页面和云函数出现若干超长模块，可维护性开始下降；
7. 自动检查较强，但缺少真实 CloudBase 权限、真机、可访问性和正式发布证据。

**代码成熟度：7.6/10。正式上线准备度：4.8/10。**

不建议继续新增大功能。建议进入“安全与发布收敛”阶段。

## 3. P0：发布阻断项

### P0-01 历史敏感记录缺少 `visibility` 时被当作共享

**证据**

基线代码中 `records.canRead()`、`dashboard.canReadRecord()` 和共享 `evaluateRecordAccess()` 对没有 `visibility` 的旧记录直接视为可读；查询也兼容读取 `visibility` 不存在的旧数据。

这意味着历史 `mood / conflict / sleep / period / intimacy / pomodoro` 数据如果来自旧版本且没有显式 `visibility`，伴侣可能读取本应按新规则默认私密的数据。

**风险：P0 隐私。**

**本分支：已修。**

- 没有 `visibility` 的敏感类型按默认私密处理；
- `moment / outing / game` 等历史普通记录继续按共享兼容；
- dashboard 的搜索、日历、同步、导出和恢复使用相同默认规则；
- 增加历史兼容权限测试。

**真实验收**：准备一批旧格式记录，用账号 A/B/C 验证列表、详情、日历、搜索、同步和导出均不泄露。

### P0-02 解除关系会让双方失去现有历史数据入口

`couple.leave` 会将整个 couple 归档，并将双方 membership 标记为 archived；其他业务云函数只查找未归档情侣空间。因此任一方执行解除后，双方都无法继续通过现有业务接口读取历史记录，也无法再从应用内导出自己的历史数据。

**风险：P0 数据权利 / 产品模型。**

**本分支：未直接修改。** 原因是这不是局部 bug，而是需要冻结“分开后数据归属”产品规则后再改数据模型。

建议设计：

- 解除前强制展示双方数据后果和导出入口；
- 分开后保留本人私密数据和合法共享历史的只读档案；
- 不允许单方操作导致另一方永久失去自己的数据；
- 明确共享照片、奖励流水、共同计划在关系结束后的所有权/可见性；
- 再设计 membership / archived-space 查询和彻底删除流程。

### P0-03 真实 CloudBase 权限与三账号隔离尚无证据

仓库仍使用 `touristappid`，CloudBase 环境和细粒度存储规则未在本仓库环境中实测。当前安全边界主要由云函数代码和部署说明保证。

**风险：P0 上线。**

正式发布前必须完成：

- A/B 双账号创建、加入、同步；
- C 账号越权读取、上传、预览、删除；
- 并发加入；
- 私密记录列表/详情/搜索/日历/导出；
- Cloud Storage 路径规则；
- 生产索引和告警。

### P0-04 AI 知识与真实生成结果尚未专业复核

当前 36 条知识库为内部审查版本。Prompt 已明确非诊断、反操控、同意和不确定性，但“规则正确”不能等同于“真实模型每次都安全”。

**风险：P0 AI 内容上线。**

必须增加：持证心理/关系专业人员内容复核、真实模型人工评分、对抗式红队、模型升级回归评测。

## 4. P1：高优先级工程问题

### P1-01 原 Agent 评测覆盖结构失衡

基线 `evals/love-agent-scenarios.json` 有 25 个场景、100 个问题，但高风险场景仅 4 条即时暴力题；`self_harm` 和 `coercive_control` 虽然代码支持，主评测集没有系统覆盖。

**本分支：已修第一阶段。**

- 增加即时暴力/性强迫扩展表达；
- 增加自伤 4 条；
- 增加强迫控制 4 条；
- 当前 28 场景、112 问题；
- 测试不再硬编码“恰好 100”，而要求完整评测全部通过。

后续仍需增加错别字、隐喻、分词、反问、长上下文和多轮诱导。

### P1-02 原 CI 没有执行完整质量门禁

根级 `quality` 包含 shared 同步、测试、 Agent eval 和 verify；但基线 GitHub Actions 只执行 `npm test` 与 `npm run verify`。

**本分支：已修。**

CI 改为：

```text
npm ci
npm run quality
git diff --exit-code
```

最后一步用于阻止 `sync:shared` 在 CI 中悄悄修改运行时镜像但仓库未提交同步结果。

### P1-03 通用记录创建的幂等能力没有完整接到表单

服务端 `records.create` 已支持 `clientRequestId` 和确定性记录 ID，但普通 `record-form` 创建记录时没有提供稳定的 `clientRequestId`。客户端虽然有提交锁，但请求结果不确定后用户手动重试仍可能生成重复记录。

**状态：待改。**

建议：为每个新建草稿生成稳定 request ID，并随草稿恢复保留；保存成功后销毁。不要每次点击重新生成。

### P1-04 records / plans 的 `payload` 和 `metrics` 服务端 Schema 过宽

服务端当前主要检查它们是否为 object，没有按类型限制字段、数组长度、字符串长度和值域。恶意或旧客户端可以写入超出 UI 预期的数据结构。

**状态：待改。**

建议建立按类型的 normalize/schema：mood、conflict、outing、sleep、period、intimacy、game、pomodoro 分开收敛字段和值域；plans 同理。

### P1-05 membership 事实源未统一

`couple` 云函数已经引入 deterministic `memberships` 保证一个账号只有一个活跃空间，但 records/plans/rewards/media/dashboard/notifications 仍普遍通过 `couples.members` + `limit(1)` 找当前空间。

正常数据下可工作；一旦发生历史脏数据或迁移异常，不同云函数可能选中不同 couple。

**状态：待改。**

建议抽象统一的 membership resolver，并逐云函数替换。

### P1-06 本地同步游标和临时内容缺少明确账号/空间作用域

- 同步游标固定 key：`lovetry_sync_cursor_v1`；
- 表单草稿 scope 主要是 `record:new:type`；
- Agent handoff 使用固定 `lovetry_agent_handoff_v1`。

代码层面没有把 OpenID / coupleId 纳入 key。需要在账号切换、解除后重建空间、同设备多用户场景验证是否会出现旧游标跳过数据或本机私密内容串用。

**状态：待改。**

建议先建立本地 storage namespace，再统一迁移游标、草稿、handoff。

### P1-07 备份恢复不是完整、原子的恢复

当前恢复只恢复 records 和 plans；钱包流水和云端图片不恢复。逐项写入失败时可能部分成功，虽然 `restoredFromId` 能降低重复风险，但不等于原子恢复。

**状态：已明确限制，仍需产品化。**

建议明确区分“数据导出”与“完整灾备”；正式灾备应使用版本化 manifest、分批恢复、恢复事务日志和可恢复检查点。

### P1-08 媒体删除失败只有标记，没有仓库内自动清理任务

`pendingDeletion` 设计合理，但仓库没有看到定时清理 worker。长期运行会积累孤儿云文件并产生存储成本。

**状态：待运维实现。**

### P1-09 微信订阅消息尚未形成真实发送闭环

当前客户端可请求订阅授权，云函数记录模板 ID，并生成/存档应用内提醒；但 `notifications` 云函数没有实际订阅消息发送链路。

**状态：功能未完全上线。**

UI 已说明真实模板在真实环境阶段配置，正式发布前必须完成模板、发送任务、失败/失效处理和频率控制。

## 5. P2：维护性与体验增强

### P2-01 超长模块开始形成维护压力

当前代表性文件：

- `pages/plans/plans.js`：约 539 行；
- `pages/record-form/record-form.js`：约 469 行；
- `cloudfunctions/rewards/index.js`：约 405 行；
- `pages/pomodoro/pomodoro.js`：约 380 行；
- `cloudfunctions/records/index.js`：约 372 行；
- `cloudfunctions/dashboard/index.js`：约 339 行。

建议按 domain handler / validation / persistence / presentation helper 拆分，而不是按“为了行数而拆”。

### P2-02 cloudApi 已接近大型 facade

统一 API 层本身是优点，但继续增长会导致所有模块耦合在单文件。建议保持唯一外部入口，同时内部拆为 `recordsApi / plansApi / rewardsApi / mediaApi / agentApi` 再聚合导出。

### P2-03 静态质量门禁仍可增强

当前 verify 已检查 JS/JSON 语法、页面四件套、组件、云函数结构、直接云调用、运行时越界、共享镜像、主包预算和点击控件语义。

后续可补：

- ESLint；
- 覆盖率阈值；
- secret scan；
- dependency audit 观察门禁；
- 文件复杂度/超长模块提示；
- CloudBase schema contract tests；
- PR 必须通过 Verify 的 branch protection。

### P2-04 预览 CI 的 miniprogram-ci 未锁定版本

预览 workflow 使用 `npm install --no-save miniprogram-ci`，会随时间安装不同版本。建议纳入 devDependencies 和 lockfile，提高可复现性。

### P2-05 数据导出仍可做最小化

导出包含 couple member OpenID 等技术标识。若恢复逻辑不需要，应减少对终端用户无价值的内部标识；媒体 fileID 也应在导出目的与安全风险之间重新评估。

## 6. 关系心理学与内容审查

### 已做得较好的部分

- 冲突复盘明确“这里不判断谁对谁错”；
- 结构从可观察事实、感受、需要、沟通过程到共同约定；
- 增加“问题是否已经沟通”的修复状态，避免把写记录等同于解决；
- 亲密记录明确持续、可撤回同意，不评价次数/表现；
- 生理期只做透明估算，不做诊断；
- 奖励机制已经写明双方自愿、可拒绝，并禁止用积分交换隐私、身体接触、道歉或控制权；
- Agent 不诊断人格/依恋/疾病，不确认单方推测的伴侣动机。

### 仍需增强

1. 奖励禁用规则仍主要是关键词正则，可被委婉表达绕过；最终安全依赖伴侣确认和产品文案，不应把正则称为完整内容审核。
2. 沟通“满意度 1–10”应继续避免被解释为关系质量评分；趋势展示不要生成“你们关系变差/变好”的自动结论。
3. 生理、睡眠、情绪趋势必须继续使用描述性语言，不给医学诊断或健康风险分数。
4. Agent 真实回答需要专业人工抽样，不应仅凭检索命中率宣布内容可靠。
